Laboratory Activity No. 1

Real-Time Multisensor Room Monitoring System — Technical Laboratory Report

PlatformIO | STM32Cube | STM32F103C8 Blue Pill | FreeRTOS | Wokwi

1. Problem and Requirements

For this laboratory, I built a simulated room monitor that runs on an STM32 Blue Pill. The device samples temperature, humidity, and relative light; detects motion; shows one selected measurement on an OLED; sounds an alarm whenever the temperature leaves its normal range; and drops into an inactive state after a stretch with no motion.

The required temperature limits are 18 °C and 30 °C, and both endpoints count as normal — the alarm only fires low below 18 °C and high above 30 °C. The implementation is built on the STM32Cube framework with native FreeRTOS APIs, not the Arduino framework.

Wokwi translates the physical system into a virtual Blue Pill circuit with a DHT22, a photoresistor module, a PIR sensor, a KY-040 encoder, an SSD1306 OLED, and a buzzer. The LDR output is expressed as a relative percentage rather than calibrated lux.

One boundary worth stating up front: the DHT22 is wired up in the Wokwi diagram and the firmware now communicates with it through a bounded single-wire driver on PA1. The driver rejects invalid frames, and the report distinguishes implemented acquisition from runtime Wokwi verification.

The MCU clock setup uses the internal 8 MHz HSI without a PLL. The HAL millisecond tick runs on TIM4 because the FreeRTOS port owns SysTick. The OLED communicates over a project-local bit-banged I2C implementation on PB6/PB7, and the buzzer is set up for a nominal 1 kHz PWM signal.

Software architecture

The application is split across sensor, display, input, alarm, motion, system-state, and RTOS-object modules. The pure decision functions for temperature alarms, encoder navigation, and system-state transitions are kept apart from the peripheral access code so they can be compiled and tested natively.

SensorTask --+--> xQueueSensorToDisplay --> DisplayTask --> SSD1306
             +--> xQueueSensorToAlarm   --> AlarmTask   --> buzzer
InputTask ------> xQueueInputToDisplay  --> DisplayTask
MotionTask -----> EVENT_MOTION --------> StateTask
StateTask ------> EVENT_ACTIVE --------> other tasks
AlarmTask ------> EVENT_ALARM ---------> DisplayTask
All task diagnostics ------------------> USART1, guarded by serialMutex

DisplayTask is the only task that touches the OLED at runtime. SensorTask publishes each sensor record to separate display and alarm queues because a queue receive consumes the item. The sensor queues each hold five SensorData records; the mode queue holds four DisplayMode values. The event group bits are EVENT_ACTIVE (StateTask owner), EVENT_MOTION (MotionTask owner), and EVENT_ALARM (AlarmTask owner). The USART1 mutex is named serialMutex in code; it protects each transmit call, not necessarily a whole printf record.

State machine

Boot -> ACTIVE
ACTIVE -- 15 seconds without motion --> INACTIVE
INACTIVE -- motion detected ----------> ACTIVE

The system boots into ACTIVE. StateTask owns EVENT_ACTIVE and applies the 15-second inactivity rule. While the system is inactive, MotionTask keeps sampling the PIR so any activity can wake it up; SensorTask skips acquisition; InputTask keeps polling but throws away mode changes; DisplayTask blanks the screen the next time it checks the state; and AlarmTask silences the buzzer.

3. FreeRTOS Architecture

All six application tasks are created in main.cpp with explicit priorities. The periodic input, motion, and sensor work uses vTaskDelayUntil() so each run stays aligned to a fixed period instead of letting the delay accumulate after every task body. Tasks waiting on queues or event groups sit in the Blocked state until their data, event, or timeout arrives.

Task Responsibility Trigger / period Priority IPC Typical blocked condition

AlarmTaskEvaluate temperature, drive buzzer PWM, publish EVENT_ALARMSensor data; 500 ms queue timeout2Alarm sensor queue and system event groupWaits up to 500 ms for sensor data
StateTaskApply ACTIVE/INACTIVE transitions and inactivity timeoutMotion event or 15 s timeout2Waits on EVENT_MOTION; owns EVENT_ACTIVEEvent wait; 500 ms delay after detecting asserted motion

The priorities follow the latency requirements. Encoder and PIR input run at priority 3 because those signals can change on a short timescale. Sensor, alarm, and state processing sit at priority 2. OLED updates run at priority 1, since a small delay on the display is acceptable and a slow display operation shouldn't outrank input or sampling work.

In FreeRTOS terms, a task that is eligible to run but waiting for the CPU is Ready; a task waiting on a delay, queue item, or event is Blocked. The periodic tasks finish their finite work and return to Blocked. All tasks and RTOS objects are created dynamically from the configured FreeRTOS heap.

4. Implementation

SensorData holds temperature, humidity, lightLevel, and motionDetected. DHT22_Read() captures the PA1 single-wire frame with bounded DWT timing; dht22Decode() checks the checksum and value range before SensorTask publishes a sample. A failed DHT22 read is logged and skipped. The LDR is sampled through ADC1 channel 0 on PA0 and lightPercentFromAdc() scales the result to 0-100% relative brightness, not calibrated lux; an ADC failure retains the last value.

DisplayMode is an enumeration with TEMPERATURE, HUMIDITY, LIGHT, and MOTION values. InputTask watches for a falling edge on encoder CLK and compares DT to decide between forward and reverse navigation, then posts the new mode to a queue; DisplayTask performs the actual OLED update. The encoder switch input is configured on PA5 but isn't processed yet.

Temperature evaluation is deliberately hardware-independent: values below 18 °C map to LOW_TEMPERATURE, values above 30 °C map to HIGH_TEMPERATURE, and everything from 18 °C through 30 °C maps to NORMAL. AlarmTask drives TIM1 channel 1 PWM on PA8 whenever the system is ACTIVE and the temperature is out of range.

The serialMutex is taken inside the _write() retarget around each HAL_UART_Transmit() call once the scheduler has started; startup output is emitted before the scheduler runs. It protects the USART1 peripheral transmit call, not necessarily an entire printf call as one indivisible record. The symbol in this project is serialMutex, not xSerialMutex.

6. Static Code Analysis

7. Engineering Discussion

The main architectural trade-off here is splitting sensor fan-out across two queues. It avoids a race in which DisplayTask and AlarmTask would otherwise compete to consume the same queue item, at the cost of publishing the same record twice. I used the event group for shared state flags because several tasks need to read the current ACTIVE and MOTION levels, and a mutex on the UART because several task contexts emit diagnostics.

One consequence of the design: the display task waits up to 2.5 seconds on its sensor queue before checking system activity and redrawing, so a mode change or an inactive transition may not show up immediately. InputTask keeps polling while inactive but discards mode changes, and the PA5 encoder switch isn't consumed. These are known limitations, not verified feature claims.

The project uses a custom FreeRTOS Cortex-M3 port, chosen for how it behaves in the Wokwi simulator — a simulator-specific engineering decision, since physical hardware testing hasn't been documented. The DHT22 protocol is now implemented with bounded timing and checksum validation; its temperature, humidity, and alarm behavior still require a recorded Wokwi run.

9. Conclusion

All told, the project delivers a modular, concurrent STM32 FreeRTOS application: six distinct tasks, queues, an event group, a serial mutex, an OLED display path, PIR-based state logic, and independently testable alarm, navigation, sensor-decoding, light-scaling, and state decisions. The recorded firmware build and 26 native logic tests pass.

The user reports that all FT-01 through FT-10 functional checks passed in Wokwi, covering sensor changes, display navigation, alarm activation/clear, PIR activity, inactivity, and reactivation. The firmware SHA tested was not recorded, and the separate FreeRTOS fault experiments remain undocumented as observed results. Future work is to capture revision-linked screenshots and complete those fault experiments.
